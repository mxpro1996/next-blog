在 C++ 或 C 语言中调用 `std::thread` 或 `pthread_create` 时，我们往往产生一种幻觉：我们在直接操控 CPU 的并发。

但剥开层层包装，你会发现：**用户态没有真正的并发原语。** 所有的“体面”都是向内核借来的，而这张借条的名字，叫作 **Futex (Fast Userspace Mutex)**。

## 一、 众生平等：Pthread 与 std::thread 的搬运本质

无论你使用的是 C++20 的信号量，还是古老的 POSIX 锁，在 Linux 环境下，它们的血缘关系极其单一：

1.  **std::thread**：它是 C++ 标准库对 `pthread` 的一次 **头文件级封装**。
2.  **pthread (NPTL)**：它是 **Glibc** 对内核系统调用（System Call）的一次 **逻辑装配**。
3.  **核心结论**：它们本身不产生“锁”，它们只是 **Futex 的搬运工**。



---

## 二、 借贷契约：Glibc 的“两头瞒”策略

Glibc 作为一个精明的中介，为了压榨性能，设计了一套**快速路径 (Fast Path)** 与 **慢速路径 (Slow Path)** 的分流逻辑：

### 1. 快速路径：自力更生 (Atomic)
当你执行 `mutex.lock()` 时，Glibc 首先会在用户态尝试一次 `atomic_cmpxchg`。
* **物理支撑**：`ldrex/strex` (ARM) 或 `lock cmpxchg` (x86)。
* **代价**：几十个时钟周期。
* **结果**：如果没人抢，直接拿锁返回。**此时不产生 Syscall，不进内核。**

### 2. 慢速路径：跨界求救 (Futex Syscall)
如果原子操作失败，Glibc 意识到“私了”不成，必须“报警”。它会发起系统调用：
`syscall(SYS_futex, &lock_val, FUTEX_WAIT, ...)`
* **物理支撑**：CPU 陷入 Ring 0，进入内核态。
* **认怂代价**：**几千个时钟周期**。涉及上下文切换、寄存器保存、进入 Wait Queue。



---

## 三、 认怂的代价：为什么 Cond Var 必然沉重？

你发现 `std::condition_variable` 必须绑定 `std::unique_lock<std::mutex>`。这暴露了用户态并发的软肋：

* **内核态**：可以关中断，保证“检查条件 + 挂起”是原子的。
* **用户态**：你没法关中断。为了防止在“检查条件”后、“进入睡眠”前被踢下车（Lost Wake-up），你必须依赖 **Mutex 这种官僚契约** 来保护整个认怂过程。

> **审计结论**：`pthread_cond` 是基于 `futex` 的**双重搬运**。它不仅要进内核，还要在唤醒后重新去抢那把 Mutex。

## 四、 绕过“中间商”：AIO 与 io_uring 的降维打击

如果你觉得 `pthread` 这个搬运工太慢（因为每个线程都要独立堆栈，且竞争频繁触发 Syscall），硬核玩家会选择直接与内核对话。

1.  **直接调用 Futex**：跳过 Glibc 的冗余检查，自己控制自旋次数，精准认怂。
2.  **io_uring (异步 IO)**：
    * **逻辑转换**：从“多个线程在 WQ 里阻塞”转变为“一个线程收割 CQ 队列”。
    * **绩效飞跃**：彻底消灭了为了等待 IO 而存在的冗余线程，将并发从“线程级同步”降级为“数据流同步”。

## 六、 结语：lazurite 的并发哲学

在用户态写代码，本质上是**在“相信托管”的舒适区里寻找性能裂缝**。

* **Atomic** 是你的特权，它让你在不惊动内核的情况下释放物理性能。
* **Futex** 是你的保单，它在你竞争失败时提供了一个安全（但昂贵）的避风港。
* **Pthread** 是你的管家，它帮你处理了所有跨平台的繁文缛节。

**既然一切皆基于托管，那么高性能编程的秘诀只有一条：**
> **尽可能在用户态利用 Atomic 解决战斗；如果非要认怂，请确保你认得有价值（批量处理、异步 IO），而不是在频繁的 Syscall 搬运中耗尽 CPU 的热量。**
